# SPEC-02: Authentication & Identity Management

**Status**: Active / Implemented
**Last Updated**: 2025-12-11

## Overview

This specification outlines the architecture for Authentication (AuthN) and Identity Management in the Enterprise SSO system. The system enforces strict multi-tenant isolation while supporting flexible Single Sign-On (SSO) providers via Google Identity Platform (GCIP).

## 1. Multi-Tenant Architecture

The system distinguishes between two layers of tenancy:

1.  **Platform (System)**: The administrative layer for managing tenants.
2.  **B2B Tenants (Customers)**: The isolated environments for end-customers.

### 1.1 Isolation Strategy
*   **Database**: Shared schema (single database) with Row Level Security (RLS) enforcement.
*   **Context**: Every database query is scoped by `app.current_tenant_id`.
*   **Service Layer**: A centralized `RLSService` manages context setting to preventing data leakage.

## 2. Authentication Flow

We utilize **Firebase Authentication with Google Cloud Identity Platform (GCIP)** to handle OIDC federation.

### 2.1 Web Login Flow (SP-Initiated)
1.  **Tenant Resolution**: User enters email -> System resolves Tenant Config (OIDC Provider).
2.  **Redirection**: User redirected to Tenant's Identity Provider (e.g., Okta, Auth0, Google Workspace).
3.  **Token Exchange**: IDP returns token -> GCIP validates -> Returns Firebase ID Token.
4.  **Session Creation**: Frontend receives Firebase ID Token.
5.  **User Sync**: Frontend calls `/api/b2b/auth/sync-user`. Backend verifies token, creates/updates user record in PostgreSQL.

### 2.2 Mobile Login Flow (Native)
1.  **Tenant Resolution**: App sends email -> API returns `oidc_provider_id` and `mobile_oidc_config` (ClientId, Issuer).
2.  **Native Auth**: App uses `react-native-app-auth` to perform OAuth flow directly with IDP.
3.  **Token Exchange**: App sends IDP's `id_token` to `/api/b2b/auth/mobile-login`.
4.  **Minting**: Backend validates ID token with GCIP, then mints a **Custom Firebase Token**.
5.  **Session**: App signs in with Custom Token.

## 3. Identity Model

### 3.1 Canonical Identity
*   **Email is the Primary Identity**: The email address is the immutable identifier for linking users across providers.
*   **UID Stability**:
    *   **Web**: UIDs generated by GCIP (e.g., `oidc.auth0-xyz`).
    *   **Mobile**: UIDs may differ (e.g., `oidc-email-hash`) if using Custom Tokens.
    *   **Reconciliation**: The `UserService` uses email to match existing user records. If a user logs in from a new device (Web vs Mobile) with a different UID but same email, the system treats them as the **same user** and does *not* create a duplicate.

### 3.2 Roles & Permissions (RBAC)
*   **Roles**: Owned by the Tenant (customizable) or System Defaults (Owner, Admin, Viewer).
*   **Permissions**: Assigned to Roles (e.g., `users:read`, `settings:write`).
*   **Enforcement**: Middleware checks `has_permission(user_id, resource, action)` before every action.

## 4. Security Controls

### 4.1 Row Level Security (RLS)
PostgreSQL policies enforce data isolation at the database row level.
```sql
CREATE POLICY tenant_isolation ON users
    USING (tenant_id = current_setting('app.current_tenant_id')::uuid);
```
Backend services **must** set the context before querying:
```python
await rls_service.set_tenant_context(db, tenant_id)
```

### 4.2 Email Verification
*   **Requirement**: Users must have `email_verified: true` in their ID token to accept invitations or join tenants.
*   **Enforcement**: API rejects unverified users for critical actions.
